# 自测与对比报告

版本范围：本文记录首次提交 `b3f40c2` 的第一版测试。后续路线、住宿和天气规则
已更新；本文的入口哈希和对比结果是历史记录，不表示后续版本已重新跑同样比较。

日期：2026-10-19（Asia/Shanghai）。结论：第一版满足这次需求，在固定证据下
能给出有条件、可取舍的行程，并能对提供的时间和预算做可复跑检查。
**没有证据证明它全面优于其他旅游 skill。** 两个对照也处理对了大多数关键约束。

## 方法与复查材料

- 三个独立上下文 agent，继承同一宿主默认模型/推理配置，未覆盖模型参数。
  每个 agent 按同一顺序回答 A/B/C 三题；每种条件仅运行一次，不是多次统计评测。
- 同一份 [题目与虚构证据](cases.md)，禁止联网查询虚构地点；三个条件都读取
  自己 skill 的相关参考文档。没有真实预订、付款或外部应用写入。
- 对照为 [Adaptive Travel Planner](https://github.com/ryunana/adaptive-travel-planner-skill/tree/c2dd8913dfc2af6ad6e42cd2440340dc0cb33642)
  和 [Travel Planner Skill](https://github.com/ZawYePhyo/travel-planner-skill/tree/a5a09563ed4d2a27650f70873430d0f0f98523ee)。
  记录了 [提交与入口文件 SHA256](upstream-versions.json)。上游文档仅在私有临时
  工作区读取，没有把上游完整 skill 或用户个人资料发布进仓库；评估未执行对照
  仓库的辅助脚本，因此不比较它们的脚本能力。
- 本 skill 的入口 SHA256：`460332ed2dce5bdec20405b3dfebbbbc59ab4a465c16370dea93abc0f12c93a1`。
  新 skill 组额外保留审计中间文件和真实 stdout；不强迫对照采用新 skill 的 JSON
  协议，也不以是否调用本项目脚本给对照扣分。
- [观察标准](rubric.md)在阅读输出之前写下，按实际行为人工判读。
  判读者是本项目作者，知道条件身份；不是盲评或独立第三方认证。

原答：[本 skill](results/new-skill.md)、[Adaptive](results/adaptive.md)、
[Travel Planner](results/travel-planner.md)。所有结果均为测试材料，不是旅游建议。

重要细节：

- B 的完整主线在三个输出中都只是**有条件方案**。馆内步行未知，加上其他零碎
  步行要控制在0.5公里内；仅凭这些材料无法证明它一定能执行。
- 本 skill 给出了游船净增 `160船票＋(45−35)返程差额＝170元`，加应急总额
  `809＋170＝979元`，超900上限79元。Adaptive 给“160元起”，Travel Planner
  给160元门票并指出时间/步行冲突；两者也都正确删掉了游船，不能将此写成它们
  推荐了超预算行程。差别在于本次输出的**增量核算更完整**。
- 本 skill 与 Travel Planner 明确把酒店附近午餐100元视作规划额度；它不是
  已核实的当地报价。本 skill 测试过程中在最终答复前修正了这项表述，不能把
  最终结果理解为模型从未产生过需要纠正的草稿。
- 本 skill 主动给主要交通和安检追加明确机动时间。两个对照也安排了部分空档，
  不能据此断言只有本 skill 会留余量。
- C 未给出日历日期。JSON 使用 `2026-11-14` 作为明确标注的同日钟点审计占位，
  不能拿它推断真实运营、星期或天气。到站入口与完成安检不同，预留时间仍是
  估计，不是进站保证。

## 检查器实测

实际运行：

```shell
python -m unittest discover -s tests -v
python scripts/validate_package.py
python realistic-travel-planner/scripts/audit_plan.py evaluation/results/new-skill-B.json --constraints evaluation/results/new-skill-B-constraints.json
python realistic-travel-planner/scripts/audit_plan.py evaluation/results/new-skill-C.json --constraints evaluation/results/new-skill-C-constraints.json
```

- 31项自动测试通过：25项检查器单元/CLI测试，6项来自实际 agent 产物的回归测试。
- B、C 原始审计均通过，stdout分别保存在
  [B审计](results/new-skill-B-audit.json) 与 [C审计](results/new-skill-C-audit.json)。
- 针对真实生成的B计划故意注入5种错误：压缩交通、漏掉已付酒店、侵占应急金、
  预约未知却去掉条件、活动重叠；均能被检查器拒绝。
- 技能创建器的 `quick_validate.py` 通过；它只检查技能格式，不证明规划质量。

审计通过只表示**所填数据**满足所填/独立约束，不证明预约有票、来源真实、
成本齐全、完整门到门组件已填全、身体能承受或活动值得。把错误价格伪装成
已核实价格、漏写一个未列为必需类别的费用、杜撰步行量，都仍可能绕过此类
检查；必须保留人工证据与完整性审查。

## 相比现有 skill，优势与不足在哪里

| 方面 | 本项目的侧重 | 对照项目的已有优势 |
|---|---|---|
| 需求确认 | 作息、体力、同行者、预算范围与体验取舍集中确认 | Travel Planner已有相当完整的偏好采集；本次也做到了 |
| 路线取舍 | 核心/可删/跳过与时间、增量费用、删除条件相连 | Adaptive已有明确的目的地取消/延期判断 |
| 数字审计 | 标准库脚本＋独立约束，错误可定位，能在CI复跑 | 对照文档也要求检查时间和预算；未据此否认其人工核验能力 |
| 天气、疲劳与国内目的地比较 | 有基本考虑，但没有专门评分模型和地图适配器 | Adaptive的天气匹配、综合负荷和国内选址流程更细 |
| 行程写入应用 | 保持可移植，不内置服务集成 | Travel Planner有更具体的Wanderlog写入流程 |

适合希望保留普通聊天体验、又希望关键时长与费用能复查的人。不适合宣称
全自动预订，或仅凭一份skill就获得实时地图、余票和完整当地体验数据。

## 真实数据与结论边界

另做了一次 [官网访问检查](live-check.md)：搜索摘要可见，正文读取及浏览器访问
失败，最终保留未知，没有编造确定结论。这只验证了失败时的信息处理，未验证
成功的实时检索、地图排程或真实出游效果。

此轮比较只有三道固定题、两个开源对照、每条件一次运行，未比较商用agent，
没有用户实游反馈、成本/延迟统计或大样本胜率。可支持的结论是：
**明确的门到门/费用契约加可执行检查是一项可维护的工程增益；尚不能据此
声称旅行推荐质量全面领先。**
