# 路线、住宿、天气交付回归

日期：2026-10-20（Asia/Shanghai）。本轮修复第一版在实际对话中暴露的问题：
有约束核验，却没有稳定交付路线；住宿仅出现在费用范围里；天气缺少预报日期
核验和对行程的具体影响；一个目标受限时，后续答复容易重复警示与额度表。

## 改了什么

- 路线：起终点、停车/入口、点位顺序、分段距离与时间、驾车和步行分开、
  徒步爬升/拍照/休息、返回与折返逻辑。无法验证的路段单独标注。
- 住宿：先判断是否过夜，再比较区域和酒店；统一日期、人数、房型、早餐、
  接驳、退改与总费用口径。当日往返也解释住宿是否有必要。
- 天气：核对发布时间、有效日期与地点；区分短期预报、趋势、季节背景和未知。
  把天气转成活动顺序、取舍与复查节点，不能用旧缓存或今天的天气代替出行日。
- 失败恢复：目标受限时继续研究匹配偏好的替代候选，保留有价值的规划部分；
  不假装恢复开放，不强行替换旅行者的体验目标，不把额度表当已核实预算。

具体规则：[trip-deliverables.md](../realistic-travel-planner/references/trip-deliverables.md)。

## 如何验证

一个独立上下文 agent 使用更新后的 skill，分别回答 [D、E 两道虚构题](module-cases.md)。
不联网、不预订、不询问用户，不读取其他评估输出。公开案例不包含真实用户的
目的地、行程或个人资料。[观察标准](module-rubric.md)在阅读答复前写下。
原始答复见 [modules-v2.md](results/modules-v2.md)。

- D提供一个封闭的原目标，以及一个有管理公告与路线证据的非售票岩棚候选；
  同时故意缺少远期天气、车辆能耗和酒店库存，检查能否完成有依据的部分。
- E提供两日路线、两家酒店的库存/退改/早餐/接驳快照，以及适用日期的天气；
  检查是否按总行程成本选择住宿，并把湖边活动排在下雨前、雨日上午安排室内。

内部计划和独立约束实际运行了附带审计器，原始stdout摘要见

## 限制

单agent、每题一次、作者判读，不是盲评或统计基准。审计只能检查所填数据；
路线完整性、天气时效和真实房态仍需来源审查。酒店位置、规则、房价和天气均为
虚构测试数据，不能用于真实预订。E没有给博物馆行李政策，答复需保留轻装假设，
不能把入馆携行李当作已核实事实。

原始答复覆盖信息较多、篇幅仍偏长。本轮验证了模块能否产出内容，尚未证明
实际对话中的简洁程度和真实检索成功率；正式回答仍应按问题规模压缩。

实际能力边界没有被文档更新消除：skill本身不附带地图算路、酒店库存或天气服务。
本轮只验证提供证据后的规划行为，没有证明当前宿主能成功获取所有实时数据。
真实检索中部分天气索引仍显示旧月份，因此不能把“检索到天气页”当成已拿到
出行日预报。数据不可得时应明确缺哪一项并继续完成其余规划，而不是编造数字。
